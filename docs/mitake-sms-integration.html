1. 結論摘要

這個專案已經有一份可以運作的三竹實作（MitakeSmsProvider）， 基本形狀是對的：POST form-urlencoded、指定 CharsetURL=UTF-8、解析 INI 風格回應、 把 statuscode 落在 0/1/2/4 視為受理 —— 最後這點與規格書附錄二完全吻合。

研究文件之後，真正需要處理的是七個落差，其中兩個會直接讓正式站發不出簡訊：

  • 端點路徑與規格書不一致（G1）—— 現有程式用 /api/mtk/SmSend，這份 B2C 文件寫的是 /b2c/mtk/SmSend。
  • 正式站 IP 必須先向三竹登記（G2）—— 沒登記會拿到 statuscode=k，本機測得過、上線就掛。

其餘五項是穩定性與成本問題：缺 clientid 會重複扣點、 沒有餘額查詢會在點數用完時無預警斷掉、簡訊失敗會讓整個 requestOtp() 拋 500。

目前沒有任何測試覆蓋這支 provider test/integration/auth-otp.test.ts 走的是 console provider， parseMitakeResponse() 沒有任何單元測試。這個函式是所有錯誤判斷的單一入口，值得補。

2. 申請與前置條件

規格書第 4 頁「三竹格式 API 發送」列了四項硬性條件，全部都是先向三竹申請、不是寫程式能繞過的：

項目規格要求對本專案的意義
API 發送權限 必須向三竹簡訊中心申請開啟 一般網頁帳號預設沒有這個權限，未開通會回 statuscode=p（沒有權限使用外部 Http 程式）
IP 鎖定 須提供「程式發送主機」與「登入網頁介面主機」的 IP，經三竹鎖定後方可使用 正式站 103.1.221.67 必須登記。未登記會回 statuscode=k（無效的連線位址）
TLS 版本 須採用 TLS v1.2 以上（v2.10 起舊版 SSL/TLS 不再支援） Node.js 20 的 fetch 預設就是 TLS 1.2+，無須額外設定
併發連線數 合併發連線數限制在 15 條以內，超過會被系統阻擋 OTP 流量遠低於此，但若日後加訂單通知簡訊的批次寄送要留意
規格書第 4 頁的重送警告，直接對應到我們的錯誤處理設計 「如果客戶端到三竹簡訊中心間的網路傳輸有狀況發生，客戶端必須以人工進行查詢， 以確定該筆(批)簡訊是否已被三竹簡訊中心收下。若省略查詢直接重送簡訊，可能造成重複發送； 若直接忽略不重送，則可能造成簡訊漏送。」

換句話說：timeout 之後不能直接重試。正解是帶 clientid（三竹端自己會去重）， 或事後用 SmQuery 查。我們目前兩者都沒有做 —— 見 G3。

3. API 規格整理

共五支 endpoint 加一個 callback。全部都是 POST， base URL 在文件中寫成 https://{三竹網域名稱}/b2c/mtk/... —— 實際網域需由三竹提供（見 G1）。回應一律是純文字，不是 JSON。

3.3 簡訊狀態查詢 SmQuery

POST https://{網域}/b2c/mtk/SmQuery　單次上限 100 筆。

帶 username / password / msgid（多筆用半形逗號分隔，需 URL Encode）。回應是 Tab 分隔、CRLF 換行：

0311216947	6	20060623103807
0311216948	4	20060623103810
0311216949	4	20060623103809

msgid  ⇥  statuscode  ⇥  statustime(YYYYMMDDHHMMSS)

注意：回覆的簡訊順序與查詢的順序無關，必須用 msgid 對回去。

3.4 帳號餘額查詢

同樣打 SmQuery，但不帶 msgid，就會被視為餘額查詢：

POST https://{網域}/b2c/mtk/SmCancel　單次上限 100 筆。只有預約中的簡訊能取消。

3.6 主動狀態回報 Callback

發送時有帶 response 欄位的話，狀態更新時三竹會以 GET 打我們指定的網址， 參數為 msgid、dstaddr、dlvtime、donetime、 statuscode、statusstr、StatusFlag。

回應格式有硬性要求 必須回 HTTP 200、Content-Type: text/plain，內容為（[LF] = ASCII 10）： 
magicid=sms_gateway_rpack[LF]msgid=8091234567[LF]
回錯格式三竹會判定回報失敗並重試。另外文件明載：發送時 statuscode < 0 的簡訊為發送失敗，不會有狀態回報。

4.4 計費長度（附錄四）

純英數（GSM 字集範圍內）一則簡訊以 160 字計算，每字 1 個字元。 但下列 GSM 擴展字集符號需前綴轉義字元（1B），以 2 個字計算：

^ { } \ [ ~ ] |

中文簡訊的計費長度，這份文件沒有寫 附錄四只規範純英數 160 字的情況。我們的 OTP 內容是中文，實際單則字數上限需向三竹確認。

目前 OTP 訊息約 38 字（【莎岡選品店】您的驗證碼是 123456，5 分鐘內有效。請勿轉傳給他人。）， 以業界慣例的中文 70 字上限來看有安全邊際，但這是推測不是文件依據。 重點在於：帳號若無長簡訊權限，超長內容會被截斷後照樣送出，不會報錯 —— 驗證碼被截掉會是無聲的故障，所以訊息長度不要再加東西。

5. 現有實作 vs 規格：落差清單

P0

G1　端點路徑與規格書不一致

現況src/lib/sms/mitake.ts:5 寫死 https://smsapi.mitake.com.tw/api/mtk/SmSend

規格文件第 5 頁寫的是 https://{三竹網域名稱}/b2c/mtk/SmSend —— 路徑是 /b2c/mtk/ 不是 /api/mtk/

影響三竹的 /api/mtk/（企業版）與 /b2c/mtk/（B2C 版）是兩組不同的服務路徑，帳號開通在哪一組就只能打哪一組。打錯會拿到 404 或權限錯誤，而且因為現有程式只在 !res.ok 時報 HTTP 狀態碼，錯誤訊息會很難懂。

處置需向三竹確認我們的帳號屬於哪一組、正確網域為何，再把 base URL 抽成環境變數（不要寫死），這樣兩種帳號都能切換。這是唯一需要外部確認才能定案的項目。

P0

G2　正式站 IP 尚未確認是否已向三竹登記

規格「並提供程式發送主機與登入網頁介面主機的 IP，經三竹簡訊中心鎖定 IP 後方可使用」

影響正式站容器從 103.1.221.67 出去。未登記 → statuscode=k（無效的連線位址）→ 所有手機 OTP 登入失效。這種錯誤本機開發完全測不出來（本機用 console provider），會在切 SMS_PROVIDER=mitake 的那一刻才爆。

處置上線前先用該主機打一次「餘額查詢」（不帶 msgid 的 SmQuery）驗證 IP 通了 —— 這支不花點數，是最便宜的連線驗證方式。

P1

G3　沒有帶 clientid，重試會重複發送、重複扣點

現況參數中沒有 clientid，回應的 [clientid] 一律是預設值 1。

規格clientid 是三竹提供的冪等機制，12 小時內重複的 ID 會直接回傳前次結果並帶 Duplicate=Y，不會真的再送一次。文件建議用 GUID。

影響現有程式 AbortSignal.timeout(15_000) 逾時就丟 Error。若三竹其實已經收下了，使用者按重送（OTP_RESEND_COOLDOWN_SECONDS = 60 秒後）就是實打實的第二則簡訊、第二次扣點。文件第 4 頁明確警告過這個場景。

處置用 crypto.randomUUID() 產生 clientid 傳入。注意這需要在 otp.ts 層決定「這是同一次請求的重試」還是「使用者主動重送」—— 前者共用 clientid，後者必須換新的。

P1

G4　錯誤未分類，且簡訊失敗會讓整個 requestOtp() 拋出

現況所有失敗都是同一個 throw new Error(...)，字串裡塞原始 body。otp.ts:74 的 await provider.send(...) 沒有 try/catch。

影響兩個問題疊在一起：
(a) 三竹暫停服務（a/b/r）這種可重試的，跟帳密錯誤（e）、IP 未登記（k）這種重試一百次也沒用的，處置方式完全相同；
(b) 簡訊送不出去時 requestOtp() 直接往外拋 —— 使用者看到的是 500，不是「簡訊服務暫時無法使用，請稍後再試」。

處置定義 MitakeError 帶上 statusCode 與 retryable 旗標； requestOtp() 補一個 { ok: false, reason: 'sms_failed' } 分支。 另外注意錯誤訊息不能把 body 原封輸出到使用者端 —— 目前只在 server 端 log，這點是對的，維持住。

P1

G5　沒有餘額查詢，點數用完會無預警斷線

現況回應裡的 AccountPoint 被 parseMitakeResponse() 解析進 Map 之後丟掉了，沒有回傳也沒有記錄。

影響點數歸零時三竹回 statuscode=s（帳務處理失敗），此時才發現已經來不及 —— 手機登入已經全站掛掉。而 AccountPoint 每次發送都會回來，資訊本來就在手上。

處置把 AccountPoint 帶進 SmsSendResult，低於門檻（例如 100 點）時寫 warn log 或發信給 SHOP_SERVICE_EMAIL。成本幾乎為零。

P1

G6　msgid 的 # 前綴未處理

現況parseMitakeResponse() 直接取 = 右邊，原樣回傳。

規格SmSend 回應範例是 msgid=#000000013（帶 #）， 但 SmQuery 的請求與回應範例都是 0311216947（不帶 #）。

影響目前 messageId 只是存著沒用到，所以還沒出事。但一旦要拿它去打 SmQuery 或比對 callback 的 msgid，帶著 # 就會查無資料（statuscode=z），而且會很難查。

處置解析時 .replace(/^#/, '')，並在註解寫明原因。

P2

G7　沒有實作 callback，拿不到最終送達狀態

現況response: '' —— 欄位有傳但值是空字串，等於沒設定 callback。

影響我們只知道「三竹收下了」（statuscode 1/2），不知道「使用者手機真的收到了」（statuscode 4）。OTP 場景下使用者收不到簡訊時，客服無從判斷是門號有誤（6）、簡訊停用（7）還是逾時（8）。

處置優先度低於前面幾項，但如果要做：開 GET /api/sms/mitake/callback，回傳 magicid=sms_gateway_rpack[LF]msgid=...[LF]，並把 StatusFlag 寫回 PhoneOtp。這個 endpoint 是公開的、無認證的，需要比對 msgid 是否為我們發出的，不能照單全收。

P2

G8　換行字元的地雷（目前未觸發，但要記下來）

規格：smbody 若要換行，必須填 ASCII Code 6，不是 \n。 目前 OTP 訊息是單行所以沒事，但日後若加訂單通知、出貨通知簡訊，直接寫 \n 會得到非預期結果。建議現在就在 mitake.ts 補上註解或一個 formatSmsBody() 轉換函式。

做對的部分

  • ACCEPTED_STATUS_CODES = {0,1,2,4} 與附錄二完全一致。
  • 明確指定 CharsetURL=UTF-8 —— 規格預設是 Big5，沒指定就是亂碼，這點抓得很準。
  • 用 URLSearchParams 送 body，& 與中文的 URL Encode 自動處理，符合規格要求。
  • normalizeTwMobile() 的 886 → 0 轉換與 v2.14 新增的號碼正規化邏輯相容。
  • 錯誤訊息只在 server 端拋出，沒有把三竹回應洩漏到前端。
  • 回應本體是純 ASCII 的 key=value，所以 res.text() 以 UTF-8 解碼不會有 Big5 亂碼問題 —— 這個湊巧是安全的。

6. 建議程式碼

以下是把 G3～G6、G8 一次補齊的 mitake.ts。G1 的 base URL 改成吃環境變數，等三竹回覆後填值即可：

import 'server-only'
import { randomUUID } from 'node:crypto'
import { env } from '@/lib/env'
import type { SmsProvider, SmsSendResult } from './provider'

/**
 * 三竹簡訊（Mitake）B2C API v2.14。
 * 文件：docs/B2C_MitakeAPI_v2.14.pdf、docs/mitake-sms-integration.html
 *
 * 回應是 INI 風格的純文字：
 *   [1]
 *   msgid=#000000013
 *   statuscode=1
 *   AccountPoint=126
 */

/** 這些 statuscode 代表三竹已受理（附錄一/二）。5~9 與所有英文字母皆為失敗。 */
const ACCEPTED_STATUS_CODES = new Set(['0', '1', '2', '4'])

/** 三竹端的暫時性狀況，退避後重試才有意義；其餘錯誤重試一百次也一樣。 */
const RETRYABLE_STATUS_CODES = new Set(['a', 'b', 'r', 'l'])

/** 餘額低於此值就開始示警。三竹點數用完會回 statuscode=s，屆時手機登入會全站掛掉。 */
const LOW_BALANCE_THRESHOLD = 100

export class MitakeError extends Error {
  constructor(
    message: string,
    readonly statusCode: string | null,
    readonly retryable: boolean,
  ) {
    super(message)
    this.name = 'MitakeError'
  }
}

export class MitakeSmsProvider implements SmsProvider {
  readonly name = 'mitake'

  async send(to: string, text: string, clientId?: string): Promise {
    if (!env.MITAKE_USERNAME || !env.MITAKE_PASSWORD) {
      throw new Error('SMS_PROVIDER=mitake 但未設定 MITAKE_USERNAME / MITAKE_PASSWORD')
    }

    const params = new URLSearchParams({
      username: env.MITAKE_USERNAME,
      password: env.MITAKE_PASSWORD,
      dstaddr: to,
      smbody: formatSmsBody(text),
      // clientid 是三竹的冪等機制：12 小時內同一個 ID 不會真的重送，只會回上次結果 + Duplicate=Y。
      // 呼叫端重試時要沿用同一個；使用者主動「重新發送」則必須換新的，否則收不到第二則。
      clientid: clientId ?? randomUUID(),
    })

    const res = await fetch(`${env.MITAKE_ENDPOINT}/SmSend?CharsetURL=UTF-8`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded; charset=UTF-8' },
      body: params,
      signal: AbortSignal.timeout(15_000),
    })

    if (!res.ok) {
      // HTTP 層失敗無從得知三竹是否已收下，當作可重試 —— 但呼叫端必須沿用 clientid，
      // 否則就是文件第 4 頁警告的「省略查詢直接重送造成重複發送」。
      throw new MitakeError(`三竹簡訊 HTTP ${res.status}`, null, true)
    }

    const parsed = parseMitakeResponse(await res.text())

    if (!parsed.ok) {
      throw new MitakeError(
        `三竹簡訊發送失敗（statuscode=${parsed.statusCode ?? 'n/a'}）`,
        parsed.statusCode,
        parsed.statusCode !== null && RETRYABLE_STATUS_CODES.has(parsed.statusCode),
      )
    }

    if (parsed.accountPoint !== null && parsed.accountPoint < LOW_BALANCE_THRESHOLD) {
      console.warn(`[mitake] 簡訊點數僅剩 ${parsed.accountPoint} 點，歸零後手機 OTP 登入會失效`)
    }

    return { messageId: parsed.msgId }
  }
}

/** 三竹的 smbody 換行要用 ASCII Code 6，不是 \n。 */
function formatSmsBody(text: string): string {
  return text.replace(/\r?\n/g, '\x06')
}

export function parseMitakeResponse(body: string): {
  ok: boolean
  msgId: string | null
  statusCode: string | null
  accountPoint: number | null
  duplicate: boolean
} {
  const kv = new Map<string, string>()
  for (const line of body.split(/\r?\n/)) {
    const idx = line.indexOf('=')
    if (idx > 0) kv.set(line.slice(0, idx).trim(), line.slice(idx + 1).trim())
  }

  const statusCode = kv.get('statuscode') ?? null
  const rawPoint = kv.get('AccountPoint')
  const point = rawPoint === undefined ? Number.NaN : Number(rawPoint)

  return {
    ok: statusCode !== null && ACCEPTED_STATUS_CODES.has(statusCode),
    // SmSend 回的 msgid 帶 # 前綴（msgid=#000000013），但 SmQuery 與 callback 用的是不帶 # 的
    // 純序號。存進 DB 前先剝掉，否則日後拿去查會得到 statuscode=z（查無資料）。
    msgId: kv.get('msgid')?.replace(/^#/, '') ?? null,
    statusCode,
    accountPoint: Number.isFinite(point) ? point : null,
    duplicate: kv.get('Duplicate') === 'Y',
  }
}

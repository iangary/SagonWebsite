這是本機正本 docs/sagon-deploy/.env.production 現在的內容。綠界三項服務都已經換成正式的，黑貓還停在測試站。

二、開賣前必須先解決的兩件事

BLK-1　黑貓指向測試站，而宅配沒辦法從後台關掉

正式站現在只要有客人選「宅配」並付款，worker 就會拿測試授權碼去 egs.suda.com.tw:8443 建單，拿回一個測試單號寫進訂單。結果是包裹永遠不會被收走，前台貨態永遠不動，而客人的錢已經收了。

後台的運送設定只有運費欄位，沒有啟用開關，所以沒辦法「先只開超商取貨」。可以走的路只有兩條：

  1. 申請黑貓正式授權碼，切 TCAT_ENV=production。這是正解。測試站與正式站的授權碼是分開申請的兩組，目前手上只有測試站那組。
  2. 在正式金鑰到手之前不要對外開賣。測試商品不掛分類、測完就封存，讓一般客人走不到結帳。

把宅配運費調到很高來勸退不算解法，客人還是選得到。

BLK-2　送檔只重建 web 會漏掉 worker

專案文件寫的是 --force-recreate web，但 worker 也吃同一份 env_file，而建物流單、開收據都在 worker 裡跑。只重建 web 的話會變成金流走正式站、物流還留在測試站，這種半切狀態最難發現。兩個一起重建：

ssh root@103.1.221.67 'cd /srv/sagon && chmod 600 .env .env.production && docker compose -f docker-compose.prod.yml up -d --force-recreate web worker'

階段 D — 部署與前置

先讓主機真的吃到新的設定，再談測試。這一段不花錢。

編號項目類別優先
D-01確認本機正本已含主機補過的值 主機那份過去是手改的，可能有本機沒有的欄位。沒合併就上傳會把它們靜靜清掉，而且要等有人用到那個功能才會壞。流程見 docs/sagon-deploy/README.md 的「一次性收斂」。 判定：欄位差異比對的輸出是空的，或每一格差異都已逐格決定過。部署P0
D-02備份主機現有的兩份 env scp 覆蓋沒有 undo，主機上留下的 .bak-MMDD-HHMM 是唯一的回退點。 判定：/srv/sagon/ 底下看得到今天時間戳的 .env.bak-* 與 .env.production.bak-*。部署P0
D-03送檔、改權限、重建 web 與 worker scp 覆蓋後權限會回到 644，等於同機器上其他程序都讀得到金鑰，所以 chmod 600 不能省。重建一定要含 worker，理由見 BLK-2。 判定：兩個容器都是新的啟動時間，且 docker compose ps 全部 healthy。部署P0
D-04容器裡的環境變數真的是正式的 重建之後直接進容器確認，不要只相信檔案內容。docker compose exec web printenv ECPAY_ENV ECPAY_MERCHANT_ID，worker 也要各查一次。 判定：web 與 worker 兩邊都回 production 與 3466995。任一邊還是 stage 就是 BLK-2 踩到了。部署P0
D-05站台本身沒壞 跑 scripts/check-drift.sh 與 scripts/smoke.sh。注意這兩支只測路由狀態碼，金流那條鏈驗不到，不能拿它當通過標準。 判定：兩支都以 0 結束，沒有非預期狀態碼。部署P1
D-06建一個測試商品 後台新增：名稱 【測試】請勿購買、售價壓到最低、庫存 3、不掛任何分類、先存成 DRAFT 確認前台看不到，再改 ACTIVE。 ⚠️ 這是正式站，ACTIVE 期間會被 sitemap 收錄、被搜尋引擎抓到。而且商品一旦被下單就刪不掉了，只會被封存，會永久留在資料庫與訂單快照裡。名字取得夠明顯。 判定：DRAFT 時前台列表、搜尋、直連都看不到；改 ACTIVE 後直連看得到。前置P0
D-07正式廠商後台設定收據字軌 登入 vendor.ecpay.com.tw 設定收據字軌。測試站設過的不會帶過來。沒設的話開立一律回「查無可使用字軌」，而佇列對這個工作設了五次重試加指數退避，log 會很吵。 字軌每期都要重新配號，記進營運月曆。 判定：後台看得到當期可用字軌。前置P0
D-08決定 ECPAY_RECEIPT_AUTO_ISSUE 目前是 true，付款成功會自動排開立收據。關掉不會少功能，後台仍可一張一張人工開立與作廢。字軌還沒設就先關，免得每筆測試都拖一串失敗的工作。 判定：知道自己現在設的是哪個值，以及 E-07 該預期什麼。前置P1

階段 E — 綠界正式環境

從這裡開始每一步都是真的。E-01 到 E-06 是同一張訂單依序走完，選「超商取貨 + 信用卡」。這個組合會讓一張訂單走過收銀台、回拋、轉 PAID、建物流單、列印標籤，正好把金流與物流串在一起驗證。

不要用宅配測，那會打到黑貓測試站。

編號項目類別優先
E-01電子地圖選店 結帳頁選「超商取貨」→ 點選店，在彈出的地圖裡選一間門市。 判定：地圖網址是 logistics.ecpay.com.tw，沒有 -stage；選完門市代號、名稱、地址自動帶回結帳頁。 地圖開不出來，或稍後建單回「找不到加密金鑰」，代表物流服務還沒開通，或開成了 B2C 而不是 C2C。後台到「物流管理 → 物流建單及查詢 → 物流廠商」確認。物流P0
E-02真卡刷卡 真實金流 付款方式選信用卡送出，用自己的卡完成刷卡與 3D 驗證。這筆錢會真的被扣，E-10 再退。 判定：導向的網址是 payment.ecpay.com.tw，沒有 -stage；刷卡成功後導回本站結果頁，顯示付款成功與訂單明細。 如果收銀台直接報錯或拒絕，八成是金鑰與環境沒配對，例如金鑰換成正式但 ECPAY_ENV 還停在 stage。金流P0
E-03回拋、訂單狀態、簽章 看後台訂單頁與 Webhook 頁。 判定：訂單 PAID（或已被 worker 推進 PROCESSING），綠界交易編號有值；Webhook 有一筆 ReturnURL 事件、已處理、簽章有效；庫存從預扣轉實扣。 簽章過得了就代表 HashKey 與 HashIV 是對的，這是整份清單裡最關鍵的一格。金流P0
E-04自動建立綠界物流單 真實金流 付款成功後 worker 會跑 create-shipment。這一步建出來是真的超商物流單。 判定：worker log 出現 create-shipment 且成功，訂單的 AllPayLogisticsID 有值，狀態轉 PROCESSING。 這一格過了才算金流與物流真的串起來。物流P0
E-05列印一段標 後台訂單頁按「列印一段標」，會開新視窗 POST 到綠界。 判定：標籤版面正確，門市、收件人、單號齊全。物流P0
E-06重入防護 對已有物流單的訂單再看建單按鈕，並手動重跑一次 create-shipment。 判定：按鈕顯示「已建立物流單」且不可用；重跑工作不會產生第二張物流單。物流P1
E-07電子收據開立 真實金流 若 D-08 設成 true，付款成功後 worker 會自動開。開出來是真的收據，要作廢才能取消。 順便驗負數品項：用一張有折扣碼的訂單開立，折扣在收據上是負數單價的品項。官方文件只寫單價可為 0，沒說可以是負的，這是程式裡未經驗證的假設。 判定：issue-receipt 成功，收據號碼寫回訂單，綠界收據後台查得到；金額等式成立，各品項單價乘數量的總和等於訂單總額。 被退件的話解法是把折扣按比例攤回各品項。收據P1
E-08ATM 取號（只驗到取號） 另開一張訂單，付款選 ATM。不需要真的去轉帳，驗到取號這一段就夠，取號走的是 PaymentInfoURL 那條獨立的路。測完讓它自然逾期。 判定：結果頁顯示銀行代碼、虛擬帳號、繳費期限，且沒有「重新付款」按鈕；訂單維持 PENDING_PAYMENT；收到取號通知信；訂單的 expiresAt 是建單後約一天而不是 30 分鐘。金流P1
E-09超商代碼取號（只驗到取號） 再開一張，付款選超商代碼。同樣不必真的去繳。 判定：結果頁顯示繳費代碼與期限，看清楚期限是幾分鐘。期限若被對齊成 30 分鐘的庫存預扣期，代表消費者只有 30 分鐘走到超商，這是上線前要處理的問題。金流P1
E-10信用卡退款 真實金流 把 E-02 那筆錢退回來。後台觸發退款，程式打綠界的請退款端點。只有信用卡能這樣退，ATM 與超商付款不支援線上退款 API。 判定：退款回應成功，後台看得到退款紀錄，綠界廠商後台該筆交易狀態轉為已退款。金流P0
E-11取消 E-04 建出來的物流單 那是一張真實的超商物流單，不取消的話超商端會有實際的取件流程。到綠界廠商後台把它取消掉。 判定：綠界後台該筆物流單狀態為已取消。物流P0
E-12作廢 E-07 開出的收據 後台作廢，填作廢原因。原因欄位上限 200 字元，超過會被截斷。 判定：作廢成功，狀態正確。收據P2

階段 T — 黑貓宅配

走哪一條路取決於正式授權碼到手了沒有。目前是路線二。

路線一：已取得黑貓正式授權碼

編號項目類別優先
T-01換成正式授權碼並重查郵碼 把 TCAT_ENV 改成 production、TCAT_CUSTOMER_TOKEN 換成正式站那組。契客代號通常兩邊共用，授權碼不是。 接著一定要重跑一次地址解析取 TCAT_SENDER_ZIP，正式站算出來的郵碼不保證和測試站一樣。注意這支腳本驗不出授權碼錯誤（實際遇過它成功、建單卻回 E009「契客資料不正確」）。 判定：地址解析回傳成功，郵碼後六碼已填進設定。回傳失敗就是憑證不對，別往下走。黑貓P0
T-02宅配建單 真實金流 開一張宅配訂單並付款，等 worker 跑建單。 ⚠️ 黑貓沒有冪等鍵，建兩張就是兩筆真實運費。建之前確認寄件地址是真的出貨地址。 判定：托運單號有值，訂單轉 PROCESSING，storage/labels/ 出現該訂單的 PDF。黑貓P0
T-03開啟託運單 PDF，立刻另存備份 後台訂單頁的「列印託運單」。 ⚠️ 黑貓的檔案編號只有 24 小時有效，過期無法向黑貓重新下載，而且目前沒有補印機制。storage/labels/ 裡那份是唯一副本。 判定：PDF 開得起來，版面與黑貓的 A4 二模樣本一致，而且已經另存到別的地方。黑貓P0
T-04重入防護 重跑建單工作，再看後台按鈕。 判定：按鈕已停用，不會再建第二張託運單。這條沒過就別上線，因為每建一張就是一筆真實運費。黑貓P0
T-05貨態輪詢與前台顯示 手動觸發一次輪詢工作，平時 worker 每 30 分鐘自動跑。連跑兩次確認去重。 判定：貨態寫入資料庫，連跑兩次不產生重複歷程；後台與前台訂單查詢頁的貨態時間軸都看得到；出貨通知信寄出。黑貓P1
T-06呼叫黑貓來收貨 真實金流 ⚠️ 這支會叫真人開車過來，而且黑貓每個收貨點每日只受理一次、無法指定時段。一天只有一次機會，排在 T-02 建完託運單之後再做。 判定：回覆是黑貓原文的集貨通知訊息；重新整理後按鈕換成今天已呼叫的狀態，沒有第二顆可按；件數填 0 或非數字會被前端擋下。黑貓P2

路線二：還沒拿到正式授權碼（目前狀態）

編號項目類別優先
T-S1不要在正式站測宅配 正式站的黑貓還指向測試站，測出來的託運單號是假的，但訂單狀態會被推進 PROCESSING，看起來像成功。要驗宅配流程就在本機用測試環境跑，配 cloudflared tunnel 和綠界測試金鑰。 判定：走查過程中沒有任何一張正式站訂單選過宅配。黑貓P0
T-S2對外開賣前補完路線一 在黑貓切到正式站之前，站台不能對一般客人開放，因為宅配沒辦法從後台關掉。測試商品不掛分類、測完立刻封存，讓一般客人走不到結帳。 判定：黑貓正式授權碼已申請、T-01 到 T-05 已完成，才把商品正式上架。黑貓P0

階段 C — 收尾與清理

編號項目類別優先
C-01封存測試商品 被下單過的商品刪不掉，只能封存。不封存的話它會留在前台、留在 sitemap。 判定：前台列表、搜尋、直連都看不到那件商品。清理P0
C-02清點所有建出來的真實單據 逐一對照：刷過的卡都退了、建過的綠界物流單都取消了、開過的收據都作廢了、黑貓託運單（若有）都處理了。 判定：記錄表裡每一筆真實單據都有對應的收尾動作與時間。清理P0
C-03把測試期間改過的設定調回正式值 尤其是 ECPAY_RECEIPT_AUTO_ISSUE。改了記得重建 web 與 worker，不是只有 web。 判定：容器裡查到的值就是你要的正式營運設定。清理P1
C-04把本機正本的異動同步上去並留一份 docs/sagon-deploy/ 在 .gitignore 裡，沒有備份在版控裡。換電腦或重灌前記得自己留一份。 判定：本機正本與主機內容一致，且正本已另外備份。清理P1

失敗處理程序

任何一步不符預期時，先停下來，不要重試、不要重按按鈕。重試會污染現場，黑貓重建單還會多花運費。

  1. 保留現場。截圖當下畫面，記下訂單編號與時間。
  2. 蒐集證據。worker log 含失敗工作的完整堆疊；後台 Webhook 該筆事件的原始內容與處理狀態；若是排程失敗，查稽核紀錄裡的排程失敗項目，之後可以手動補派。
  3. 寫成問題單。格式是操作步驟、預期、實際、證據四段，再決定修復或繼續。
  4. 如果錢已經扣了而流程沒走完，先把退款做掉再查問題。客人的錢不該等你除錯。

先把一件事講清楚：假帳號、假留言、假評價這一段我不做。

「做臉、做留言、做推銷」如果指的是建立人設帳號假裝素人留言推薦自家商品，這件事我不會幫忙實作，理由有三個，而且每一個都是實質風險，不是道德潔癖：

1. 會被停權，而且會連累登入功能。Meta、Google、Threads、Dcard 的條款都禁止虛假帳號與協同性造假行為（coordinated inauthentic behavior）。被抓到不只掉貼文，是粉專與廣告帳號一起停 —— 而你的網站現在把 Facebook 當成 SSO 登入提供者（src/lib/auth/index.ts:129），Meta 商業帳號被停會連帶影響會員登入。

2. 台灣有明文規範。《公平交易法》第 21 條管不實廣告；公平會〈薦證廣告處理原則〉要求薦證者與廠商有利益關係時必須揭露。找 KOC 業配合法，偽裝成素人不合法。

3. 對 SEO 是負分，而且會反噬你的結構化資料。Google 垃圾內容政策把假評價列為操縱行為。假評價寫進 Review 資料表、再輸出成 aggregateRating，等於親手把違規證據交給 Google；一旦被判定，整站失去複合式搜尋結果資格，要人工複審才能救回。

合法、而且長期效果更好的替代方案，本文都寫了：§5 的自動評論邀請信（真客人、真評價，可全自動）、§6 的 KOC 合作信範本（含揭露句）、§6 的官方帳號貼文腳本（可排程全自動）。真評價還有一個假評價永遠拿不到的好處：能合法接上 aggregateRating，讓 Google 搜尋結果長出星星（見 §2 的 S-02）。

2. SEO：缺口與優先序（主表）

優先序的判準是「投入 ÷ 影響」，不是難度。P0 是上線第一週就該有的，缺了會讓後面所有努力都量不到、看不到。

ID優先項目現況與該做什麼
S-01P0完全沒有數據GSC / GA4 全 repo grep 不到 gtag、GoogleAnalytics、google-site-verification。現在你對這個站的自然流量一無所知 —— 哪個關鍵字帶人進來、哪一頁跳出、商品頁有沒有被索引，全部是黑箱。 做法：① 到 Search Console 用 DNS TXT 驗證 chenkuanyi.com.tw（DNS 驗證比檔案驗證好，涵蓋所有子網域）→ 手動提交 /sitemap.xml。② 裝 @next/third-parties 的 GoogleAnalytics 元件到 [locale]/layout.tsx，量 ID 走 NEXT_PUBLIC_GA_ID 環境變數（沿用現有 src/lib/env.ts 的 zod schema，設成 optional）。③ GA4 開電商事件：view_item、add_to_cart、begin_checkout、purchase。
S-02P0搜尋結果沒有星星aggregateRating 這是投報率最高的一項。product-reviews.tsx:51 已經算出平均分並顯示在頁面上，但 product/[slug]/page.tsx:92 的 JSON-LD 完全沒有 aggregateRating。等於分數算了、畫了，卻沒告訴 Google。 補上之後，Google 搜尋結果會在標題下方長出 ★★★★☆ 與評論則數，點擊率的提升通常比排名前進一名還多，而且不需要等排名。前提是評價必須是真的 —— 你的 Review 綁 orderItemId @unique，這個條件天生成立。實作見 §3。實作紀錄 已完成 —— lib/seo/structured-data.ts 的 productJsonLd；平均與則數改由 getProductReviewStats（全部已核准評論）提供，同一組數字同時餵給畫面與 JSON-LD。
S-03P0分享出去是一片空白OG image 找不到任何 opengraph-image 檔，root metadata 的 openGraph 也沒有 images。現在把首頁連結貼到 LINE 群組或 FB，出現的是沒有圖的純文字卡片 —— 在以 LINE 分享為主的台灣市場，這等於把社群導流的轉換率砍掉一大半。 做法：① 新增 src/app/[locale]/opengraph-image.tsx（Next 的 ImageResponse，1200×630，放店名＋標語＋主視覺）當全站預設。② 商品頁已經會帶 images: [product.images[0].url]，但要確認那張圖接近 1.91:1，直式商品圖在 FB 會被裁掉主體。③ 順便補 src/app/icon.png 與 apple-icon.png（目前也沒有）。實作紀錄 已完成 —— [locale]/opengraph-image.tsx（1200×630，已實際出圖確認中文正常）、app/icon.tsx、app/apple-icon.tsx。
S-04P0沒有品牌身分資料Organization / WebSite 只有商品頁與 FAQ 頁有結構化資料，全站沒有 Organization 也沒有 WebSite。Google 因此不知道「莎岡選品店」是一個品牌實體，也不知道你的官方社群帳號、客服信箱、統編對應到誰。 做法：在 [locale]/layout.tsx 輸出一份全站 JSON-LD，含 Organization（name、url、logo、sameAs 指向你的 IG／FB／LINE OA、contactPoint 用 SHOP_SERVICE_EMAIL）與 WebSite（含 SearchAction，讓搜尋結果可能長出站內搜尋框）。sameAs 是把社群經營成果回灌給品牌搜尋的關鍵，這條把 §6 的社群工作和 SEO 接起來。實作紀錄 已完成 —— siteJsonLd() 在 [locale]/layout.tsx 輸出。sameAs 讀 SHOP_FACEBOOK_URL / SHOP_INSTAGRAM_URL / SHOP_LINE_URL，目前三個都空著，等你提供帳號網址。
S-05P1麵包屑沒有結構化資料 Breadcrumbs 元件有畫在畫面上，但沒有對應的 BreadcrumbList JSON-LD。補上之後搜尋結果的網址列會變成「首頁 › 睡衣 › 商品名」，而不是一長串網址。商品頁、分類頁各補一份。實作紀錄 已完成 —— breadcrumbJsonLd()；麵包屑資料只定義一次，畫面與結構化資料共用同一個陣列，不會漂移。

S-02 — 讓搜尋結果長出星星

在 src/app/[locale]/product/[slug]/page.tsx，把已核准評價的統計一起查出來（Prisma 的 aggregate），接進現有的 jsonLd：

// 只統計 APPROVED —— PENDING / 被退回的不能算進去
const stats = await db.review.aggregate({
  where: { productId: product.id, status: 'APPROVED' },
  _avg: { rating: true },
  _count: { _all: true },
})

const jsonLd = {
  '@context': 'https://schema.org',
  '@type': 'Product',
  name,
  sku: product.sku ?? product.slug,          // S-07
  // ...現有欄位不動...

  // 一則評價都沒有時必須整個省略。
  // 給 reviewCount: 0 會被 Google 判為無效結構化資料，比不給還糟。
  ...(stats._count._all > 0 && stats._avg.rating
    ? {
        aggregateRating: {
          '@type': 'AggregateRating',
          ratingValue: Math.round(stats._avg.rating * 10) / 10,
          reviewCount: stats._count._all,
          bestRating: 5,
          worstRating: 1,
        },
      }
    : {}),
}

兩個一定要守住的規則：

1. 頁面上看得到的分數，必須等於 JSON-LD 裡的分數。product-reviews.tsx:51 目前是對所有傳進來的評價取平均並四捨五入到小數一位 —— 要確認那個查詢也只取 APPROVED，兩邊口徑不一致會被判定為欺騙性標記。
2. 沒有評價就不要輸出 aggregateRating（上面的展開式已處理）。

4. 「完全自動化」的誠實答案

簡短版：內容產出、發佈排程、成效回報可以做到接近全自動；「互動」與「品牌判斷」不能，也不該。

我的建議是把行銷拆成三層來想：

環節自動化程度說明
商品 feed 產出與更新可全自動Merchant Center 與 Meta 目錄定時來抓你的 feed 網址，價格庫存自動同步。寫一次，永久不用管。
sitemap／IndexNow 通知可全自動sitemap 已經是動態的；再加一個上架時主動 ping 搜尋引擎的 hook。
評論邀請信可全自動出貨後 N 天自動寄「請給個評價」。這是「做留言」唯一正確的做法：讓真客人留真評價。你已經有 bullmq 排程與寄信基礎建設。
棄車信／補貨通知可全自動結帳中斷 N 小時後寄信；缺貨商品到貨時通知登記過的人。轉換率通常是所有 email 裡最高的兩種。
社群排程發文可全自動用官方 API（Meta Graph API 發 FB 粉專／IG、LINE Messaging API 發 OA 推播）。發自己的官方帳號完全合規，排程隊列一週跑一次。
成效週報可全自動GSC API + GA4 Data API 拉數字，每週一早上寄一封「上週搜尋曝光／點擊／熱門關鍵字／轉換」給你。
文章與貼文草稿半自動AI 生成初稿可以自動，但發佈前要有人看過。理由不是品質，是責任：商品成分、洗滌方式、授權宣稱、退貨天數寫錯，是消費爭議不是文案問題。建議流程：排程觸發生成 → 存成 DRAFT → 寄信通知你 → 你在後台按「發佈」。你花的時間是每篇 3 分鐘，不是 3 小時。
回覆留言與私訊半自動可以自動偵測＋草擬建議回覆，但按送出的是人。社群帳號公開回錯話的代價很高，而且客訴、退貨、尺寸諮詢這三類本來就需要判斷。站上已有 SupportChat，可以先把它接成「AI 草擬 → 你確認」。
廣告投放半自動受眾、素材、預算分配可以自動化上傳與輪替，但預算上限與停損要你決定。
假帳號、假素人留言、買評價不做理由見文件開頭。這一項不是「難以自動化」，是「不該做」 —— 而且它會直接破壞上面那些真的有效的東西（帳號被停、結構化資料被撤、品牌搜尋出現負評討論串）。

換算成你實際要花的時間：上面的自動化全部做完之後，穩定期你每週的行銷投入大約是 —— 審 2 篇文章草稿（10 分鐘）＋ 審一週社群貼文（15 分鐘）＋ 回留言私訊（每天 10 分鐘）＋ 看週報（5 分鐘）。其餘全部是機器在跑。這已經非常接近「完全自動化」能到的實務極限了。

5. 可以寫進 repo 的六件自動化

都對得上現有架構（Next route handler、Prisma、bullmq、既有寄信服務），不需要新的基礎建設。

ID要做的東西落點與說明
A-01Google／Meta 商品 feed src/app/api/feeds/google-merchant.xml/route.ts —— 查 status: ACTIVE 的商品，輸出 Merchant Center 的 RSS 2.0 格式（g:id、g:title、g:description、g:link、g:image_link、g:availability、g:price、g:brand、g:condition、g:shipping）。跟 sitemap.ts 一樣設 dynamic = 'force-dynamic'（建置階段沒有資料庫）。Meta 目錄可以吃同一份，或另出一支 CSV。 設定完 Merchant Center 排程每日抓取，之後價格與庫存永遠自動同步，不用再手動上傳。robots.ts 的 /api/ disallow 不影響 —— Merchant Center 的抓取器不看 robots.txt 的 * 規則，但保險起見可以把 feed 放在 /feeds/ 而不是 /api/。實作紀錄 已完成 —— src/app/feeds/google-merchant.xml/route.ts ＋ lib/seo/product-feed.ts（12 項單元測試）。放在 /feeds/ 而不是 /api/，正是因為 robots.txt 擋掉整個 /api/，這點在實作時確認過了。
A-02評論邀請信「做留言」的正解 訂單狀態轉為「已送達」後 +7 天，用 bullmq 排一個延遲任務，寄一封信給客人，內含直達 /account/orders/[id]/review 的連結（這個頁面已經存在）。 評價進 PENDING，你在後台審核後轉 APPROVED，接著自動被 S-02 的 aggregateRating 統計到，變成搜尋結果上的星星。從一封自動信到 Google 上多一顆星，整條路完全自動、完全合規。審核只擋人身攻擊與廣告，不要擋負評 —— 全五星反而降低可信度，而且刻意篩掉負評是《公平交易法》上的不實廣告風險。實作紀錄 已完成 —— lib/orders/review-invite.ts ＋ worker 的 send-review-invites 排程（10 項整合測試，含「兩輪排程同時跑只會寄一封」的併發測試）。新增 Order.completedAt 與 Order.reviewInviteSentAt 兩個可為空的欄位，migration 是純新增，對正式資料無風險。
A-03棄車信與補貨通知 棄車：Cart 有內容但 N 小時無結帳 → 寄一封提醒（有會員 email 才寄）。補貨：商品頁缺貨時給「到貨通知我」按鈕，寫進新的 StockAlert 表，庫存回補時觸發。 兩者都掛在既有的 bullmq queue 上。寄信頻率要克制，棄車最多兩封、補貨一封，被大量標記垃圾信會拖垮整個網域的送達率。
A-04社群排程發文 scripts/social-queue.ts ＋ 一張 SocialPost 表（platform／bodyText／mediaUrl／scheduledAt／status／externalId）。後台一個簡單列表可編可排程；到點由 worker 呼叫官方 API 發出。 API：FB 粉專與 IG 走 Meta Graph API（需要粉專的 long-lived token 與 pages_manage_posts 權限，IG 發圖要先 media 再 media_publish 兩步）；LINE OA 走 Messaging API 的 broadcast／narrowcast（推播有免費則數上限，超過要付費，排程前要擋）。全部都是發自己的官方帳號，完全合規。
A-05每週成效報表 scripts/weekly-report.ts：GSC Search Analytics API 拉「上週曝光／點擊／平均排名／前 20 名關鍵字」，GA4 Data API 拉「工作階段／加入購物車／結帳／營收」，組成 HTML 寄到 SHOP_SERVICE_EMAIL。 重點看兩個訊號：「有曝光但點擊率低」的關鍵字（→ 標題與描述要改）、「排名 8–20 名」的關鍵字（→ 補一篇內容就可能進前五，投報率最高）。
A-06上架即通知搜尋引擎 商品上架／文章發佈時打 IndexNow API（Bing／Yandex 收），並在後台留一顆「請求 Google 重新索引」的按鈕。小事，但新商品被收錄的時間可以從幾天縮到幾小時。

腳本 1 ｜ IG／FB 貼文 · 單品聚焦
凌晨三點翻身的時候，你會知道睡衣選得對不對。 〔商品名〕用的是〔材質〕，〔材質的一個具體好處，例如：貼著皮膚不黏、翻身不會纏住手臂〕。 我們挑它的原因很簡單 ——〔一句選品理由，講你真正在意的事〕。 ・尺寸：〔S / M / L〕 ・顏色：〔米白 / 霧灰 / 藕粉〕 ・洗滌：〔可機洗，建議洗衣袋，30 度以下〕 連結在個人檔案 → 〔商品頁網址〕 #韓國睡衣 #〔材質〕睡衣 #居家服 #莎岡選品店 #睡衣推薦

腳本 2 ｜ 官網 Journal 文章 · 知識文（SEO 主力）
標題：〔莫代爾、天絲、純棉睡衣差在哪？一次講清楚該怎麼挑〕 網址：/journal/〔modal-tencel-cotton-pajamas〕 第一段（150 字內，直接回答，不鋪陳）： 　　〔莫代爾最軟、垂墜感最好，適合怕悶熱的人；天絲最涼、吸濕排汗最快，適合夏天與容易流汗的人；純棉最耐洗、最不容易起毛球，適合天天穿天天洗。以下是三種材質在「觸感、透氣、耐洗、價格」四個面向的完整比較。〕 H2：〔三種材質的來源與差別〕 H2：〔怎麼挑：四種常見情況〕 　　H3：〔怕熱、容易流汗〕 　　H3：〔皮膚敏感〕 　　H3：〔孕期與產後〕 　　H3：〔送禮不知道對方喜好〕 H2：〔洗滌與保養：延長壽命的四件事〕 H2：〔常見問題〕（3–5 題，會被 FAQ 結構化資料吃到） 文末：〔挑好了嗎？看看我們的〕→ 掛 2–3 張相關商品卡
為什麼這樣寫：第一段就把答案講完，是為了 Google 的精選摘要與 AI 搜尋摘要 —— 它們只抓「直接回答問題」的段落。H2／H3 對應真實的搜尋句型。這篇文章的目標不是賣東西，是接住「還在比較、還沒決定買誰」的人，賣東西是文末那幾張卡片的事。
腳本 3 ｜ LINE OA 推播（字要少，則數要省）
【莎岡選品店】〔新品到貨〕 〔韓國〇〇系列長袖睡衣，四色到齊〕 〔本週下單滿 1,500 免運〕 〔商品頁短網址〕 （不想收到訊息可封鎖此帳號）

腳本 5 ｜ 評論邀請信（配合 §5 A-02 自動寄出）
主旨：〔您的〇〇睡衣還合身嗎？〕 〔王小姐〕您好， 您在〔8 月 12 日〕購買的〔商品名〕已經送達一週了。 穿起來還習慣嗎？ 如果方便的話，想請您花一分鐘留下使用心得 —— 不論好壞我們都想知道，這會直接影響我們接下來挑什麼、不挑什麼。 〔留下評價〕（按鈕 → /account/orders/〔id〕/review） 如果有任何不合適的地方，也可以直接回信給我們， 〔七日鑑賞期內可退換〕。 莎岡選品店
為什麼這樣寫：明講「不論好壞都想知道」有兩個作用：提高回覆率，以及證明你沒有只徵求好評（這是薦證廣告規範上的關鍵差別）。同時提供「直接回信」的出口，可以把本來會變成公開負評的不滿，先接到私下處理。絕對不要寫「給我們五星就送優惠券」 —— 那是用對價換取評價，違反平台政策也違反公平會規範。
腳本 6 ｜ KOC／部落客合作邀約信（合法的「找人推薦」）
主旨：〔莎岡選品店〕想邀請您試穿我們的韓國睡衣 〔您好，我是莎岡選品店的〇〇〕。 我們看過您〔某篇具體的內容，要真的看過並講得出細節〕， 覺得您對〔材質／居家風格〕的講法跟我們挑貨的標準很接近， 想邀請您試試我們的〔商品名〕。 合作方式： ・我們寄一件〔商品名〕給您，不回收 ・〔是否有稿費：有的話寫金額，沒有就寫「本次為無償贈品合作」〕 ・希望您在〔平台〕發一則使用心得，形式與內容由您決定 ・〔不指定評價方向 —— 覺得不好也請照實寫〕 唯一的請求： 依公平會〈薦證廣告處理原則〉， 請在貼文中明確標註〔#廠商邀約〕或〔#合作〕， 說明您與我們的合作關係。這對雙方都是保護。 如果有興趣，回信告訴我尺寸與收件資訊就可以了。 〔您的名字〕 莎岡選品店　〔客服信箱〕
為什麼這樣寫：「不指定評價方向」＋「必須標註合作」這兩句，就是合法業配與違法假素人的分界線。而且這樣做的實際效果更好：讀者看得出來這是業配還願意看完的內容，說服力遠高於一眼假的「素人真心推薦」。對方願意在這個條件下合作，你才真的找對人。

6.4 社群帳號的開設順序

不要一次開五個然後全部荒廢。建議順序：

  1. Instagram —— 服飾寢具的視覺主場，也是 Reels 的來源。
  2. LINE 官方帳號 —— 台灣回購率最高的通路。而且它是你自己的名單，平台演算法改了也帶不走。
  3. Facebook 粉專 —— 客群年齡偏高的話優先度提前；同時是 Meta 動態商品廣告（A-01 的 feed）的必要條件。
  4. Threads —— 成本低，同一批文案可直接複用。
  5. 官網 Journal —— 嚴格說不是社群，但它是唯一一個不會被演算法收走的資產，優先度其實應該排第一。

五個帳號的網址開好之後，記得回填到 S-04 的 sameAs —— 那一步才讓社群經營的成果被算進品牌的搜尋權重。

對時間的預期要正確：SEO 的內容投資通常要 3–6 個月才看得到明顯的自然流量成長，第一個月幾乎一定是平的。這不是做錯了。真正該在第一個月看的指標是「索引涵蓋率」（GSC 裡商品頁有沒有被收錄）與「結構化資料有沒有報錯」，不是流量。
想要快的話，付費廣告（Google Shopping／Meta DPA）是另一條路，而且 A-01 的 feed 兩邊共用 —— 做一次，SEO 與廣告同時受益。

8. 我需要你提供的資訊

  1. 你已經有哪些社群帳號？（IG／FB／LINE OA／YouTube 的網址）—— S-04 的 sameAs 要填，沒有的話就照 §6.4 的順序開。

  4. 商品有沒有 GTIN／條碼？有的話 A-01 的 feed 品質會好很多，Merchant Center 的比對也更準。

  7. 行銷預算的量級？決定純做 SEO 與內容，還是同時開 Google Shopping／Meta 廣告。

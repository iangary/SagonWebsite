1. CI 完全沒有跑測試。.github/workflows/deploy.yml 只 build Docker image，沒有 lint / typecheck / vitest / playwright。現在的 333 項測試等於只在你本機跑，任何人推 main 都能把壞掉的程式碼推上 GHCR。

功能缺口清單

SPEC.md 第 5 節已經誠實記錄了大部分缺口。以下把它們跟我額外掃到的合併，並標上「上線前是否必要」。P0 = 沒有它不能對外營業（法規或金流完整性），P1 = 上線後一個月內會痛，P2 = 有空再做。

F-03綠界物流狀態碼對照表補齊ecpay/logistics.ts 的 STATUS_CODES 只收常見碼。認不得的碼不會亂改狀態（安全的預設），但代價是消費者看到的貨態會停在舊狀態不動。需對照綠界完整文件補齊四家超商 + 兩家宅配。物流P0待開發

B. 金流與付款回拋

風險最高的一節。SPEC 3.7 定義了五條安全規則，目前只有第 2 條的簽章演算法本身有測試，其餘四條的實際行為都沒有自動化驗證。

ID檢核項目 / 判定標準層級優先現況
B-01CheckMacValue 產生與驗證（含 .NET URL encode 差異、參數順序無關、竄改任一欄位即失敗、缺 CheckMacValue 視為失敗）單元P0已有 14 項
B-02AIO 送單參數組裝判定：金額為整數（無小數）、ItemName 以 # 分隔且長度不超限、TradeDesc 已編碼、MerchantTradeNo 不超過 20 字且唯一、ExpireDate／StoreExpireDate 與 STOCK_RESERVATION_MINUTES 對齊（SPEC 3.7 明說要對齊，這條沒測就可能出現「繳費成功但庫存已釋放」）。單元P0待開發
B-03驗簽失敗的回拋不被處理判定：送出簽章錯誤的 ReturnURL 請求 → 訂單狀態不變、庫存不變、事件落地並標記簽章無效、後台不允許重送（SPEC 3.7 明確要求）。整合P0已有（整合測試）
B-04金額不符時付款標記失敗且不出貨判定：簽章正確但 TradeAmt 與訂單 totalAmount 不同 → 訂單不轉 PAID、庫存不轉實扣、記錄異常。這是防「竄改金額低價成交」的唯一防線。整合P0已有（整合測試）
B-05回拋冪等：同一筆重送不重複扣庫存判定：同一份 payload 送兩次 → 第二次直接回成功、庫存只扣一次、只寄一封信。同時測「事件指紋唯一約束」在併發送達時也成立（兩個請求同時進來）。併發重複送達由 recordWebhook 捕捉 P2002 唯一約束衝突處理（F3 修復）。整合P0已有（整合測試）
B-06正式環境拒絕模擬付款判定：ECPAY_ENV=production 且回拋帶 SimulatePaid=1 → 當作未付款並記錄異常。測試站則正常處理。整合P0已有（整合測試）
B-07RtnCode != 1 不轉為已付款判定：簽章正確但回報付款失敗 → 訂單留在 PENDING_PAYMENT、庫存維持預扣、不寄付款成功信。整合P0已有（整合測試）
B-08前台導回（OrderResultURL）不能改變付款狀態判定：直接對 /api/ecpay/payment/return 送一份「看起來成功」的表單 → 訂單狀態完全不變。這條是 SPEC 3.7 第 1 條，也是最容易在重構時被誤傷的地方。整合P0待開發
B-09ATM／超商取號回拋（PaymentInfoURL）判定：虛擬帳號／繳費代碼、銀行代碼、繳費期限寫入訂單，訂單仍是未付款，並寄出取號通知信。ATM 期限以天計、超商以分鐘計，兩種都要測。整合P1已實測未自動化
B-10處理失敗時回失敗碼讓綠界重送判定：模擬 DB 錯誤 → HTTP 回應為綠界認得的失敗字串（不是 200 OK）、錯誤訊息寫入事件、後台看得到未處理事件與原因。整合P1待開發
B-11後台手動重送 Webhook判定：重送成功後事件轉為已處理、副作用（庫存、寄信）不重複發生；簽章無效的事件重送按鈕不可用。整合P1待開發
B-12結果頁輪詢判定：結果頁在背景通知尚未到達時顯示「處理中」，輪詢約 30 秒；期間注入付款成功 → 畫面自動變為已付款，不需重整。payment-poller.tsx 目前無測試。E2EP1待開發
B-13完整結帳 E2E（三種付款方式各一次）判定：加購物車 → 填收件 → 選配送 → 選發票 → 送出 → 導向綠界（驗證送出的表單欄位正確）。目前 E2E 只到「結帳頁可存取」。E2EP1待開發
B-14綠界測試站真卡刷卡判定：在收銀台輸入測試卡號完成 3D 驗證 → 收到真實 ReturnURL → 訂單轉 PAID、庫存實扣、寄信、收據開立。README 承認這段沒做過，只用 simulate script 驗過。步驟見 docs/manual-test-stage.md M-1。手動P0待執行
B-15正式環境金流冒煙測試判定：上線後用正式商店代號下一筆真實小額訂單走完全流程（含退刷或作廢），確認白名單、網域、憑證、收據字軌都對。手動P1待執行
B-16ATM 逾期入帳安全網判定：訂單已被取消（逾期或人工）後才收到成功回拋 → 訂單不復活，payment 標記 PAID 並寫入 failReason「逾期入帳：訂單已取消但仍收到付款，需人工退款」，後台訂單頁可見。搭配 F1 修復：ATM 的庫存預扣期已對齊綠界 ExpireDate（下限 1 天），此安全網是最後防線。整合P1已修復（整合測試覆蓋）

C. 訂單建立與庫存

防超賣的條件式 UPDATE（SPEC 3.5）是這個系統最精巧的一段程式，而它目前沒有任何測試。這一節必須在真實 Postgres 上跑，不能用 mock——mock 掉的正好是要驗證的那個併發行為。

ID檢核項目 / 判定標準層級優先現況
C-01金額計算：小計、三種折扣碼、免運門檻看折扣後金額、空車、券條件驗證單元P0已有 22 項
C-02兩人同時搶最後一件判定：庫存 1，兩個 createOrder 併發（真的併發，不是循序）→ 恰好一個成功，另一個收到「庫存不足，最多可購買 N 件」，reservedStock 最終為 1 而非 2。這是整個系統最重要的一條測試。整合P0已有（整合測試）
C-03庫存不足時整筆交易回滾判定：多品項訂單中有一項庫存不足 → 沒有任何訂單被建立、其他品項的 reservedStock 也沒被佔用、優惠券使用次數沒被計入。整合P0已有（整合測試）
C-04庫存三段生命週期判定：成立 → reservedStock +n、stock 不變；付款 → stock -n、reservedStock -n；取消 → reservedStock -n、stock 不變。任一階段結束後 stock ≥ reservedStock ≥ 0 恆成立。整合P0待開發
C-05逾期釋放與付款通知的競態判定：逾期 job 與付款回拋同時處理同一筆訂單 → 結果只有兩種（已付款＋實扣，或已取消＋釋放），不會出現「已取消但庫存被實扣」。SPEC 3.5 說釋放前會在交易內重讀狀態，這條就是驗證那個保護。整合P0已有（整合測試）
C-06逾期釋放排程判定：超過 STOCK_RESERVATION_MINUTES 未付款 → 轉 CANCELLED、釋放庫存、寄出取消通知；未逾期的訂單不受影響；已付款的訂單絕不會被掃到。整合P1待開發
C-07訂單內容是快照判定：下單後改商品名稱／價格／下架／刪圖 → 訂單明細、後台訂單頁、通知信、收據內容全部維持下單當時的值。整合P1待開發
C-08結帳前商品被下架判定：購物車有商品，管理員把它改成 DRAFT／ARCHIVED → 結帳被拒絕，錯誤訊息指名是哪一件，要求先移除。整合P1待開發
C-09折扣碼在結帳瞬間被用完判定：總量剩 1 的折扣碼被兩人同時使用 → 一人成單、一人收到「請移除折扣碼後重試」，使用次數不會變成 2。整合P1已有（整合測試）
C-10訂單狀態機的合法／非法轉換判定：逐一驗證 SPEC 3.6 的表格——管理員只能設 PROCESSING／SHIPPED／COMPLETED／REFUNDED；PENDING_PAYMENT／PAID／CANCELLED 不開放手動；管理員取消只限未付款訂單；COMPLETED 不被物流回拋推回 SHIPPED。整合P1待開發
C-11後台調整庫存不得低於 reservedStock判定：有 3 件被預扣時把庫存改成 2 → 拒絕並提示，不會出現負的可售量。整合P1待開發
C-12訂單編號產生規則（唯一、長度符合綠界 20 字上限、物流單號為訂單號 + L）單元P2待開發

    我的建議是 (a) + CI 用 services:，最快也最不容易壞。你同意的話請確認本機 Postgres 可以讓我建新資料庫。
